PyObject Anatomy & Object Layout

Standard 64-bit PyObject Structure:

+-------------------+--------------------+------------------------+
| ob_refcnt (8B)    | ob_type (8B)       | Object Data Payload    |
| (Reference Count) | (Pointer to Type)  | (Value / Dict Pointer) |
+-------------------+--------------------+------------------------+

For containers (list, dict, tuple, user objects), a PyGC_Head (16 bytes) precedes the PyObject to link nodes in the generational doubly-linked lists.

Descriptor Protocol Mechanics

Descriptor Priority in Attribute Lookup:

  1. Data Descriptors (implementing both __get__ and __set__) take precedence over instance dictionary.
  2. Instance __dict__ is checked next.
  3. Non-Data Descriptors (implementing only __get__, e.g. normal methods) take effect if absent in instance dictionary.
  4. Class __dict__ is checked.
  5. __getattr__ fallback is called if attribute lookup fails.

Staff & Principal Engineer Interview Questions
1. How does CPython's memory allocator (PyMalloc) work, and why does it use Arenas, Pools, and Blocks? ▼
CPython bypasses the OS malloc() for small object allocations (≤ 512 bytes) using PyMalloc to eliminate OS system call overhead and reduce heap fragmentation. The hierarchy consists of:
  • Arenas (256 KB): Allocated directly from the OS virtual memory via mmap or malloc.
  • Pools (4 KB): Carved out of arenas, each dedicated to a single fixed size-class (multiples of 8 bytes: 8, 16, 24, ... 512).
  • Blocks: Slices within a pool allocated to individual PyObjects. Free blocks are tracked via singly-linked free-lists inside the pool header without extra metadata overhead.
2. Explain CPython's Generational Garbage Collector cycle detection algorithm. ▼
Reference counting cannot reclaim cyclic references (e.g. A references B, and B references A). CPython solves this using a tri-generational tracing collector (Gen 0, 1, 2):
  • Every container PyObject is preceded by a PyGC_Head and linked into doubly-linked lists.
  • The GC copies ob_refcnt to a temporary gc_refs field.
  • For each object in the generation, it iterates over referenced objects using tp_traverse and decrements their gc_refs.
  • Objects whose gc_refs drops to 0 are exclusively referenced from within the cycle and marked as unreachable candidates.
  • Surviving objects are promoted to older generations (Gen 0 → Gen 1 → Gen 2).
3. How does Python 3.11+ Adaptive Specializing Bytecode (PEP 659) enhance runtime performance? ▼
PEP 659 introduces a tier-1 adaptive interpreter. When generic instructions (such as BINARY_OP, LOAD_GLOBAL, or CALL) are executed repeatedly, the interpreter monitors the types passing through. If types stabilize (e.g. always adding two integers), the bytecode is dynamically replaced in-place with specialized instructions (like BINARY_OP_ADD_INT) accompanied by inline cache entries (CACHE ops). If the type assumption is later violated, it deoptimizes back to the generic opcode.
4. What is the difference between Data Descriptors and Non-Data Descriptors during attribute lookup? ▼
A Data Descriptor defines __set__ and/or __delete__ (in addition to __get__). Because it controls mutation, Python gives it higher precedence than the instance's own __dict__. Conversely, a Non-Data Descriptor only implements __get__ (such as regular methods); if an instance attribute exists with the same name in instance.__dict__, the instance attribute shadows the non-data descriptor.
